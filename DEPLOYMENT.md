# Narrator — Deployment Guide

Narrator deploys as three pieces: a static frontend on **Vercel**, and an API + background
worker on **Render**, both pointed at the same managed Postgres and Redis instances. No
Kubernetes, no container orchestration beyond what Render's Blueprint gives you.

## Prerequisites

- A Render account (for the API, worker, Postgres, and Redis)
- A Vercel account (for the frontend)
- A Stripe account with two recurring Prices created (Starter ₹500/mo, Pro ₹1,500/mo)
- An AWS S3 bucket + an IAM user with `s3:PutObject`/`s3:GetObject` on that bucket
- (Optional) A Google Cloud OAuth 2.0 Client ID, if you want "Continue with Google"
- (Optional) Credentials for a real TTS/lip-sync provider — without them the render pipeline
  falls back to bundled local stub assets, which is fine for a demo but not for production video
  quality

## 1. Backend → Render

### 1a. Deploy via Blueprint

The repo root has a `render.yaml` Blueprint defining:
- a managed **Postgres** database (`narrator-postgres`)
- a managed **Redis** instance (`narrator-redis`)
- a **web** service (`narrator-api`) built from `backend/Dockerfile`, health-checked on `/health`
- a **worker** service (`narrator-video-worker`) built from the same Dockerfile, running
  `node dist/videos/videos.worker.js` instead of the HTTP server

In the Render dashboard: **New → Blueprint**, point it at this repo, and Render provisions all
four resources from `render.yaml`. Or from the CLI:

```bash
./scripts/deploy-render.sh
```

### 1b. Set the secrets Render can't infer

`render.yaml` marks vendor credentials as `sync: false` (Render won't invent values for these) —
set them in the dashboard for **both** `narrator-api` and `narrator-video-worker` after the first
deploy:

| Variable | Where to get it |
|---|---|
| `FRONTEND_URL` | Your Vercel deployment URL, e.g. `https://narrator.vercel.app` |
| `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET` | AWS IAM console / S3 bucket you created |
| `STRIPE_SECRET_KEY` | Stripe Dashboard → Developers → API keys |
| `STRIPE_WEBHOOK_SECRET` | Set after step 1c below |
| `STRIPE_PRICE_STARTER`, `STRIPE_PRICE_PRO` | Stripe Dashboard → Product catalog → your ₹500 / ₹1,500 recurring Prices |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_CALLBACK_URL` | Google Cloud Console → APIs & Services → Credentials (only on `narrator-api`; the worker doesn't need these) |
| `AVATAR_PROVIDER_API_KEY`, `AVATAR_PROVIDER_BASE_URL` | Your TTS/lip-sync vendor (only needed on the worker) |

`JWT_SECRET` is auto-generated by the Blueprint (`generateValue: true`) — you don't need to set
it, but if you rotate it, do so on the `narrator-api` service only (the worker doesn't verify
JWTs).

### 1c. Point Stripe's webhook at Render

In the Stripe Dashboard → Developers → Webhooks → **Add endpoint**:
- URL: `https://<narrator-api>.onrender.com/api/billing/webhook`
- Events: `checkout.session.completed`, `customer.subscription.updated`,
  `customer.subscription.deleted`, `invoice.paid`

Copy the generated signing secret into `STRIPE_WEBHOOK_SECRET` on `narrator-api`.

### 1d. Point Google OAuth at Render (optional)

In the Google Cloud Console OAuth client, add an **Authorized redirect URI**:
`https://<narrator-api>.onrender.com/api/auth/google/callback`
— matching whatever you set `GOOGLE_CALLBACK_URL` to.

### 1e. Run database migrations

`synchronize: true` is enabled outside production, but **production uses migrations**, not
auto-sync. Before (or right after) the first deploy:

```bash
cd backend
npm run migration:generate -- src/migrations/Init
npm run migration:run
```

Point `DATABASE_URL` at the Render Postgres connection string (found in the Render dashboard)
when running this locally, or run it as a one-off Render Job/Shell against the deployed database.

### 1f. Promote an admin user

There's no self-serve way to become an admin (`role: "admin"` gates every `/admin/*` route).
After you've registered your own account, promote it directly in Postgres:

```sql
UPDATE users SET role = 'admin' WHERE email = 'you@company.com';
```

## 2. Frontend → Vercel

`frontend/vercel.json` configures the Vite build and SPA rewrites.

1. In Vercel: **New Project**, import this repo, set **Root Directory** to `frontend`.
2. Set the environment variable `VITE_API_BASE_URL` to your Render API's public URL plus `/api`,
   e.g. `https://narrator-api.onrender.com/api`.
3. Deploy. Or from the CLI:

```bash
./scripts/deploy-vercel.sh
```

Update `FRONTEND_URL` on the Render API service to match your final Vercel URL (needed for
Stripe Checkout/Portal return URLs and the Google OAuth redirect target) and redeploy the API.

## 3. Post-deploy smoke test

1. Visit the Vercel URL → Landing page loads.
2. Sign up → lands on `/dashboard` with 20 free credits.
3. `/editor` → generate a video → job appears as `queued` then (once the worker picks it up)
   `processing` → `completed` with a playable preview.
4. `/pricing` → subscribe to Starter → redirected to Stripe Checkout (test mode: card
   `4242 4242 4242 4242`) → redirected back with the plan upgraded and credits topped up.
5. `/profile` → on a Pro/Enterprise account, create a team and invite a second (already
   registered) account by email.
6. Hit `GET /health` on the API directly — should return `{ "status": "ok" }` with no auth.

## 4. Local development (for comparison)

See `README.md` for the full local setup (Docker Compose for Postgres/Redis, `npm run start:dev`
for the API, `npm run worker` for the render worker, `npm run dev` for the frontend). Local dev
does not require Stripe/Google/AWS credentials to boot — those integrations simply no-op or use
local fallbacks until configured, so you can exercise the render pipeline and credit system
end-to-end before wiring up any vendor.

## 5. Scaling notes

- **Worker throughput**: bump `WORKER_CONCURRENCY` (env var, default `2`) or scale the
  `narrator-video-worker` service to more instances in Render — BullMQ handles multiple
  consumers on the same queue safely.
- **Database**: Render's managed Postgres plans scale vertically; there's nothing in the schema
  that assumes a single-writer setup, but connection pooling (e.g. PgBouncer) is worth adding
  before you scale the API service horizontally past a handful of instances.
- **Moving past a monolith**: see `ARCHITECTURE.md`'s closing section and `PRD.md`'s Phase 4
  roadmap for when to split the render worker onto its own autoscaled fleet.
